# KB-4DVar: Kármán vortex demonstration

This repository contains a research implementation of **Koopman-operator-based
four-dimensional variational data assimilation (KB-4DVar)** applied to a
Kármán vortex test case. It combines an existing two-dimensional
Navier–Stokes forward solver with EDMD-based surrogate dynamics and an
approximate adjoint for iterative initial-state correction.

**Scope:** This is a research-code example, not a fully packaged numerical
simulation application. It includes observation files and two optimization
scripts but has not been verified to reproduce every figure or table in the
associated manuscript on a clean machine. Numerical settings may need
adjustment for available memory and compute time.

## Repository contents

| Path | Purpose |
|---|---|
| `main_grad.py` | KB-4DVar using fixed-step gradient descent. |
| `main_lbgf.py` | Initial gradient step followed by SciPy L-BFGS-B optimization. The filename reflects the original code. |
| `calc_edmd_adj.py` | EDMD fitting, time evolution, and the approximate adjoint. |
| `calc_ns_field.py` | Python/ctypes interface to the Fortran forward solver. |
| `calc_dct.py` | Optional 2-D DCT filtering utilities. |
| `obsdata_controller.py` | Loads pseudo-observations and constructs observation masks. |
| `ns_model/` | Modified 2-D Navier–Stokes solver and its input file. |
| `observe_u.zip`, `observe_v.zip` | Included pseudo-observations of the velocity components. |
| `set_config.yml` | Assimilation, observation, and EDMD settings. |
| `build.sh`, `build_win.bat` | Builds the Fortran shared library on Linux and Windows. |

## Requirements

- Python 3 with the packages listed in `requirements.txt`.
- A compatible **gfortran** compiler. On Linux, `make` is optional if
  using `build.sh`. On Windows, use a MinGW-w64/gfortran installation
  compatible with the Python process architecture (typically 64-bit).
- Sufficient RAM for full-field snapshot matrices and singular value
  decomposition. The supplied mesh and EDMD rank may be computationally
  demanding; this is **not** a quick-running example by default.

## Installation and execution

From a terminal in the **repository root**:

### Linux

```bash
python -m pip install -r requirements.txt
bash build.sh
python main_grad.py
# or: python main_lbgf.py
```

The build produces `ns_model/calc_forward_ns.so`.

### Windows (Command Prompt)

```bat
py -m pip install -r requirements.txt
build_win.bat
py main_grad.py
REM or: py main_lbgf.py
```

The build produces `ns_model\calc_forward_ns.dll`. If Python cannot load
this DLL because it cannot locate the gfortran/MinGW runtime libraries, set
`KB4DVAR_DLL_DIR` to the directory containing those dependencies before
running the Python script. For example:

```bat
set "KB4DVAR_DLL_DIR=C:\path\to\mingw64\bin"
py main_grad.py
```

**Paths:** Run commands from the repository root because the Fortran solver
reads `ns_model/4DVar.inp` using a relative path. The Python entry points
also change into their own directory when launched as scripts.

## Configuration and outputs

- `set_config.yml`: number of global/local optimization loops, observation
  interval, EDMD rank and lifting order, and optional DCT filtering.
- `ns_model/4DVar.inp`: forward model parameters, mesh size, and number
  of integration steps. Keep the number of snapshots, assimilation steps,
  and observation time indices consistent if you change these settings.
- `DMD.dct_threshold: -1.0` (included setting) disables DCT filtering.
  When positive, the current implementation filters the **EDMD spatial
  modes** along each grid axis; it does not prefilter the input snapshots.
- Console progress is shown during optimization. `main_lbgf.py` can also
  write GIF animations when `SAVE_ANIM = True`; the default is `False`.

No large simulation-output datasets are generated by default. The supplied
observation ZIP files are inputs and should remain in the repository root.

For a quick check of the Python helper routines (no forward simulation):

```bash
python -m unittest discover -s tests -v
```

## Methodological notes and limitations

The approximate adjoint is implemented as described by the KB-4DVar research
code, not as a tangent-linear/adjoint derivation of the physical solver.
The example applies corrections in the EDMD-extended state space. The
physics solver is periodically rerun so that EDMD can be reconstructed from
updated initial conditions. The L-BFGS-B script evaluates an approximate
adjoint direction and should not be assumed to provide the exact gradient
of the original nonlinear simulation.

The included pseudo-observations are specific to the supplied grid and
observation-point indexing. This demonstration should not be interpreted as
an independently validated reproduction package for every experiment in the
paper. No performance or accuracy guarantee is made for altered parameters.
